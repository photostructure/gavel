## State definitions

A row records that an item was examined at its version marker. A newly discovered item starts **Unexamined**, regardless of its GitHub state. Keep its decision separate from implementation coverage.

| Decision       | Meaning                                                                                   |
| -------------- | ----------------------------------------------------------------------------------------- |
| Unexamined     | No completed assessment for the current upstream version.                                 |
| Accepted       | Implement the stated scope, or confirm that the fork already implements it.               |
| Retain fork    | Reject the proposed replacement and keep the fork's behavior; record the concrete reason. |
| Not applicable | No fork action: superseded implementation, withdrawn report, obsolete mode, or no defect. |
| Deferred       | Examined but postponed; record the missing work or the condition for reconsideration.     |

| Resolution | Meaning                                                                                   |
| ---------- | ----------------------------------------------------------------------------------------- |
| Open       | The requested behavior has no verified implementation in the fork.                        |
| Partial    | Some of the proposal exists; the reason identifies adopted, missing, and rejected parts.  |
| Resolved   | The accepted scope is implemented and verified; record commits or inherited-fix evidence. |
| —          | No implementation is required by this decision.                                           |

**Resolved means resolved in this fork.** An upstream issue closing, a PR merging, or a decision being accepted does not establish that resolution. Partial or open coverage on a Retain fork or Deferred row does not authorize implementing its rejected or postponed scope.

## Updating this index

1. Read this file and inspect current Git history and outstanding changes before comparing upstream work. Preserve work from other tasks.
2. Fetch upstream main and enumerate PRs and issues with pagination. Include old items updated or reopened since their last examination; the highest issue number is not a review cursor.
3. Compare a PR's current head SHA with its recorded SHA, and an issue's `updated_at` with its recorded timestamp. Re-examine changed items. Also revisit unchanged items when upstream base changes, new discussion changes a decision's premise, or fork changes affect the behavior used to justify that decision.
4. For a changed item awaiting examination, set Decision to Unexamined. Preserve the previous decision and version marker in a dated record before replacing them; keep existing implementation evidence. If its marker and decision premises are unchanged, reuse the recorded disposition.
5. After examination, record the exact upstream marker, review date, fork baseline, decision, resolution, reason, and implementation or verification evidence. Use full PR SHAs and ISO 8601 issue timestamps. Never advance a marker merely because metadata was fetched.
6. Update the row alongside an accepted implementation. Record the resulting commit SHA once known; mark Resolved only after the accepted scope passes verification. Do not reopen rejected feature work merely to make its coverage complete.
7. Add a dated review record for substantial comparisons or reproductions and link it from the row. Change the complete-triage date and inventory totals only after a complete pass; an individual update does not advance the inventory checkpoint.

Each row's **Reviewed / fork** value is its review date and fork comparison commit, not its last formatting date. Commit IDs in the reason identify delivered changes. Rows seeded from the first pass link back to its common evidence below; later edits should link their own evidence when it differs.
